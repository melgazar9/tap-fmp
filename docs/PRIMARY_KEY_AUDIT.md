# tap-fmp primary-key audit & remediation plan

Audit date: 2026-06-18. Covers all **258 concrete streams** (every class with a `name=`).
Per-family tables are below; this header holds the root cause, the cross-cutting defects, the
recommended fix mechanism, and the migration. Grounding: stream `schema` definitions in code are
authoritative for fields; FMP endpoint URL + WebSearch used for semantics (the FMP docs site is
403-blocked to automated fetch and the API is quota-capped).

## Root cause
`generate_surrogate_key(record)` (`helpers.py:141`) hashes the values of **every field in the
record** (`sorted(data.keys())`). `FmpRestStream.post_process` (`client.py:386`) writes that hash to
`record["surrogate_key"]` when `_add_surrogate_key=True`, and most streams set
`primary_keys=["surrogate_key"]` (directly or via `FmpSurrogateKeyStream` client.py:391,
`CompanySymbolSurrogateKeyStream`, `StatementStream`, `TtmStream`, `EsgStream`, `CalendarStream`,
`IncrementalDateStream`, `BaseBulkStream`, …).

**The loader upserts on `primary_keys`** (confirmed). So whenever ANY field changes between syncs the
whole-row hash changes → a new PK → a new row is inserted instead of updating the logical row.
Anything with a volatile field (price, volume, market_cap, ratios, estimates, scores, holdings) grows
without bound. Reported symptom: two `company_profile_by_symbol` rows for AAPL differing only by
`price`/`market_cap`, three weeks apart.

## Treatment legend
- **N** — natural key, latest-only (overwrite). Reference data / current-state snapshots, no history.
- **T** — time-series; key on the payload's own date/period; revisions overwrite that period.
- **P1** — point-in-time history; payload carries its own `timestamp`/`date`; key on entity+that field.
- **P2** — point-in-time history wanted but NO native time field; add synthetic `_fmp_extracted_date`
  and key on entity+that column.
- **E** — append-only event; key on the stable id the record exposes (`url`/`link`/composite).

surrogate_key column per stream: `drop` / `keep→hash(PK)` (stable, deterministic, join-safe) /
`keep→whole-row (PIT)` (rare; only an intentional date-less append snapshot).

## Cross-cutting defects (read before the per-family tables)

### Tier 0 — streams with NO usable primary key TODAY (loader appends EVERYTHING, dups even when content is identical)
These never got a surrogate PK wired up, so the loader has nothing to dedup on. More severe than the
surrogate bug. Fix = give each a real PK (and drop any dead `surrogate_key` column).
- `rating_snapshot` — no `primary_keys`, no surrogate. → `["symbol"]`
- `company_screener`, `exchange_variants` — no `primary_keys`, no surrogate field. → `["symbol"]`
- `crypto_quotes`, `crypto_quotes_short`, `forex_quotes`, `forex_quotes_short` — declare a
  `surrogate_key` column that is **never populated (always NULL)** and have no PK. → P1/P2 keys + drop the dead column.
- `cot_report` — no declared PK, yet still computes a (unused) whole-row surrogate. → `["symbol","date"]`
- `cot_analysis_by_date` — no PK, no surrogate column. → `["symbol","date"]`
- `market_risk_premium` — `_add_surrogate_key=True` but no `primary_keys` declared, so the surrogate
  is computed but not used as a key. → `["country"]`

### Tier 1 — schema-blocking: recommended natural key CANNOT be formed without a schema change
- `company_executives` — schema has **no `symbol`** field; the partition symbol is never written to
  the record. Add a `symbol` Property + a `post_process` that injects `context["symbol"]` (mirror
  `CikProfileStream`), then key `["symbol","name"]`. Today rows can't even be tied to their company.
- `stock_peer_comparison` — record describes the **peer**, not the queried company; the parent symbol
  is dropped. Add a parent-symbol column before any natural key works.

### Tier 2 — mechanical gotchas when changing keys / dropping the surrogate
- `surrogate_key` is `required=True` in most schemas → dropping the column means removing the
  `th.Property` AND clearing `_add_surrogate_key`, or the NOT-NULL/required check fails.
- Pagination field `_part` (e.g. `company_profile_bulk`, `etf_holder_bulk`) is added at
  `PaginatedBulkStream.post_process` **before** the hash → it currently pollutes the surrogate and
  must be excluded from any PK and any redefined hash.
- `eod_bulk` emits synthetic `__TIMEOUT_FAILURE__` skip-records (bulk_streams.py ~1400) that would
  land as real PK rows — filter them.
- Several recommended PK columns are nullable today (`date`, `url`, `link`, `cusip`) → must be
  enforced NOT NULL (and de-collapsed) before use as a Postgres PK.
- Type inconsistencies to clean up (join hazards, not all PK-breaking): `financial_ratios.date` is
  `StringType` vs `DateType` siblings; `DateType` vs `DateTimeType` across chart/interval/technical;
  `ipos_*` `filing_date` typed `StringType`.

### Reconciliation — `reported_currency` in statement PKs
The statements and bulk analysts disagreed. **Default: keep it OUT** of the PK — it is one value per
(symbol, fiscal_year, period), so adding it doesn't dedup and risks re-introducing dups if the
representation ever changes. **Add it only** if a symbol can file the SAME period in two currencies
(rare dual-filers) — verify against the data first. Flagged as an open decision.

## Recommended fix mechanism (one small refactor + per-stream keys)
1. **Generalize the hash:** `generate_surrogate_key(data, fields=None)` — when `fields` is given, hash
   only those (sorted) instead of the whole row.
2. **Add a class attribute** `surrogate_key_fields = None`. In `post_process`, when
   `_add_surrogate_key` and `surrogate_key_fields` is set, compute the surrogate over only those
   fields (→ a stable `keep→hash(PK)` value). This makes the surrogate deterministic from the natural
   key and removes the dup behavior wherever a single-column key is still wanted.
3. **Per stream:** set `primary_keys` to the recommended natural key (tables below). Where the
   decision is `drop`, remove the `surrogate_key` Property and set `_add_surrogate_key=False`.
4. **P2 streams:** inject `_fmp_extracted_date` (extraction time truncated to the chosen grain) in
   `post_process` and include it in `primary_keys`. Grain (per-day vs per-sync) is a knob.

## Migration (target-postgres will NOT auto-rewrite an existing PK constraint)
Per affected table: (a) change keys in the tap; (b) dedupe existing rows keeping `max(_sdc_sequence)`
per the NEW natural key; (c) add the unique/PK constraint; (d) thereafter the tap upserts correctly.
Fresh tables can instead be full-refresh reloaded. Review `scripts/schema_migration_audit.py` first —
it may already help here.

### Open decisions
- **Short-quote streams (company_quote_short, company_batch_quote_short, batch_mutualfund_quotes, batch_etf_quotes, batch_exchange_quote): N vs P2.** Recommending **N** (latest-only per `["symbol"]`). These have no native time field. If the user wants intraday history of price/change/volume from the SHORT endpoint specifically, switch to **P2**: add `_fmp_extracted_date` (truncated to chosen grain, e.g. minute) and PK = `["symbol","_fmp_extracted_date"]`. Tradeoff: P2 retains a price/volume snapshot trail but grows by one row per symbol per capture; N keeps the table compact and relies on the full-quote streams (company_quote / etf_price_quotes) — which DO carry `timestamp` — for true history. Recommend N because full-quote history is already covered.
- **company_price_change: N vs P2.** Recommending **N** (overwrite per `["symbol"]`) since the rolling windows are point-in-time derivations that go stale immediately. P2 (`["symbol","_fmp_extracted_date"]`) only if the user wants to snapshot how the rolling-window figures looked on each capture date. Recommend N.
- **P1 timestamp granularity / collisions:** For the full-quote streams keyed on `["symbol","timestamp"]`, if two syncs occur within the same epoch second for the same symbol (quote `timestamp` is second-resolution), the later sync UPDATES the earlier row (correct PIT behavior — same observed second = same logical observation). Confirm this second-level grain is acceptable; if finer history is desired the tap would need to add capture time, which the API does not provide.

### Notes
- **surrogate_key for P1 streams:** recommending `keep→hash(PK)` (redefine `generate_surrogate_key` to hash only the PK fields `symbol`+`timestamp`) rather than `drop`, so the existing single-column `surrogate_key` PK and any downstream joins keep working while becoming stable/1:1 with the natural key. If no downstream dependency exists, `drop` + composite PK `["symbol","timestamp"]` is equally valid.
- **All 14 streams currently have `surrogate_key` as their ONLY primary key** (inherited from `FmpSurrogateKeyStream`, client.py:394) and it is whole-row — this is the source of the duplicate-row bug for every stream here.
- **company_quote vs company_batch_quote** (and mutual_fund_price_quotes / etf_price_quotes) share the identical full-quote schema and the same logical key; if both batch and per-symbol variants land in the same DB table they will deduplicate cleanly under `["symbol","timestamp"]`, but if they write to SEPARATE tables that is fine too — no cross-stream conflict.
- **batch_exchange_quote** partitions by `exchange` (quote_streams.py:272-278) but the SHORT_QUOTE_SCHEMA record has no `exchange` field, so `exchange` cannot be part of the PK without a schema change; `symbol` alone is the correct natural key (a symbol belongs to one exchange).
- No stream in this family lacks a `symbol` field, so all recommended PKs are formable from the existing schema (the P1 streams already have both `symbol` and `timestamp`).

### Open decisions
- **company_profile_by_symbol / company_profile_by_cik (N vs P2):** Recommend **N** (overwrite latest, key `["symbol"]` / `["cik"]`). These rows are ~95% static reference data; the only churn is the embedded quote fields (price, market_cap, change, change_percentage, volume, average_volume, beta, last_dividend) which are exactly what produced the reported 2-row AAPL dup. Those live values are already captured by `company_market_cap`/quote streams, so keeping profile history adds noise, not signal. Tradeoff: if the user specifically wants point-in-time profile snapshots (e.g. CEO/sector/employee-count history), switch to **P2** with a synthetic `_fmp_extracted_date` (truncated to day) and PK `["symbol","_fmp_extracted_date"]` — but prefer N unless that history is explicitly wanted.
- **company_share_and_liquidity_float / all_shares_float (N vs P2):** Recommend **N** keyed `["symbol"]` because the FMP doc states only current float is served and the `date` is just the as-of stamp. If the user wants a float time series, **P2** with `["symbol","_fmp_extracted_date"]` (do NOT key on the payload `date` alone — it's a single moving snapshot, not a guaranteed-distinct period). Note FMP has a separate legacy historical-share-float endpoint that is not wired up here.
- **company_executives (N vs P2):** Recommend **N** (current roster) keyed `["symbol","name"]` after the schema fix. P2 with `_fmp_extracted_date` only if executive-roster history (pay/active changes over time) is wanted.
- **stock_peer_comparison surrogate_key:** Recommend `keep→hash(PK)` over `drop` once the queried symbol is added, because the natural key spans two symbol columns (parent + peer) and a single hashed join column is convenient downstream; either is defensible.

### Notes
- **company_executives — missing `symbol` (blocking, schema change required).** The schema (lines 337-347) declares only `title, name, pay, currency_pay, gender, year_born, active, title_since` — there is NO `symbol` field, and `CompanyExecutiveStream` defines only `get_url`, so the partition symbol set in `query_params` (client.py:412-413) is never written to the record. The recommended `["symbol","name"]` PK CANNOT be formed without (1) adding `th.Property("symbol", th.StringType)` to the schema and (2) a `post_process` that sets `row["symbol"] = context["symbol"]` (the same pattern `CikProfileStream.post_process` uses for `cik`, company_streams.py:130-132). Until then the stream literally cannot identify which company an executive belongs to — the surrogate key is the only thing making rows distinct.
- **stock_peer_comparison — partition symbol dropped (schema change required).** `/stable/stock-peers` returns one row per peer company; the record's `symbol`/`company_name`/`price`/`mkt_cap` describe the PEER, not the queried company. The stream (lines 150-162) has no `post_process`, so the queried (parent) symbol is lost. To key these rows you must add a parent-symbol column (e.g. `th.Property("requested_symbol", th.StringType)` set from `context["symbol"]` in a new `post_process`) and key `["requested_symbol","symbol"]`. Without that, multiple parent companies sharing a peer collide, and the volatile `price`/`mkt_cap` cause dups under the current surrogate key.
- **delisted_companies / all_shares_float / latest_mergers_and_acquisitions / search_mergers_and_acquisitions** all declare `surrogate_key` as `required=True` in-schema and set `_add_surrogate_key=True`; dropping the column means also removing it from the schema and clearing `_add_surrogate_key` (or these will fail the NOT NULL/required check). Same applies to every stream marked `drop` above that inherits `_add_surrogate_key=True` via `CompanySymbolSurrogateKeyStream` (company_streams.py:16-23).
- **company_share_and_liquidity_float `date` is DateTimeType, not DateType** — if the user instead chooses to key on the payload date, the time component would make it effectively a per-instant key and dups would recur; this is why N (or P2 on a truncated synthetic date) is recommended rather than `["symbol","date"]`.
- **executive_compensation uses `cik` not `symbol` for stability** — `symbol` is present but `cik` is the more stable issuer identifier across ticker changes; `name_and_position` distinguishes multiple executives within the same filing year. Confirm `cik` is always populated (it is the FMP issuer key for this governance endpoint).
- **company_market_cap / company_batch_market_cap / historical_market_cap confirmed OK** — all three already key `["symbol","date"]` and none declares a `surrogate_key` column (company_market_cap additionally sets `_add_surrogate_key=False`). No change needed; they are the correct template the other dated streams here should follow.

### Open decisions
- **actively_trading — N vs P2.** Recommend **N** (`["symbol"]`, latest-only): it is a current-membership list and FMP exposes no observation date. Tradeoff: you lose the day-by-day record of when a symbol entered/left the actively-trading set. If the user wants that history, switch to **P2** with `_fmp_extracted_date` (daily grain) and PK `["symbol","_fmp_extracted_date"]`.
- **company_screener — N vs P2.** Recommend **N** (`["symbol"]`): it is a live screener snapshot, and the canonical use is "current universe matching filters." Tradeoff: no point-in-time history of price/market_cap (those are better sourced from the dedicated `/quote*` and `historical-market-cap` endpoints). Choose **P2** (`["symbol","_fmp_extracted_date"]`) only if the user explicitly wants screener-state history.
- **exchange_variants — N vs P2.** Recommend **N** (`["symbol"]`): one current profile row per exchange-listed variant. Tradeoff: profile fields (price/dcf/employees) won't be tracked over time; if needed, use **P2** with `_fmp_extracted_date`.
- **surrogate_key for company_screener / exchange_variants.** Since neither currently has a surrogate_key column, the simplest fix is to **drop** (declare `primary_keys=["symbol"]` and never add a surrogate). If a single-column join key is desired downstream, instead **add** a `surrogate_key` redefined to `keep→hash(PK)` (hash only `symbol`). Recommend drop unless a downstream join needs the single column.

### Notes
- **No declared PK at all (critical):** `CompanyScreenerStream` and `ExchangeVariantsStream` extend non-surrogate base classes, set neither `_add_surrogate_key` nor `primary_keys`, and have no `surrogate_key` in their schemas. With the SDK default (no key), the Postgres loader has nothing to UPSERT on → these tables **append every row on every sync** (worse than the surrogate-key bug). Both need an explicit `primary_keys=["symbol"]`.
- **symbol_changes lacks a single-field natural id:** schema exposes only `date`, `company_name`, `old_symbol`, `new_symbol` — no accession/url/id. The recommended composite `["date","old_symbol","new_symbol"]` is the only stable identity available; if FMP could emit two distinct changes for the same old→new pair on one day this would collide, but that is not expected for symbol-change events.
- **Whole-row-hash fragility (the main bug) applies to:** `company_symbols`, `financial_statement_symbols`, `cik_list`, `symbol_changes`, `actively_trading`, `available_exchanges` — all inherit `FmpSurrogateKeyStream` (`primary_keys=["surrogate_key"]`, whole-row hash). Any benign field edit (currency correction, exchange `delay` change, name normalization) mints a new PK and inserts a duplicate logical row. All should move to the natural keys above and drop the surrogate column.
- **`available_sectors/industries/countries` are already correct** (natural-key PKs, no surrogate, `_add_surrogate_key` False via base default) — listed for confirmation only; no change needed.
- `SymbolChangesStream` is NOT mixed with any selection/partition mixin (unlike the others) — fine, it is a single global endpoint.

### Open decisions

- **key_metrics_ttm / financial_ratios_ttm / financial_scores (N vs P2).** Their CODE schemas carry ONLY

### Notes

- **`reported_currency` and the PK.** `reported_currency` is present on almost every stream here (income/balance/

  which is the opposite of the fix. Exception to flag: if a symbol can legitimately file the SAME fiscal period in

- **`enterprise_values` lacks fiscal_year/period** (only `date`), so it cannot use the family-standard

- **`financial_ratios.date` is typed `th.StringType`** (line 515) while every sibling uses `th.DateType` — a

  already sets it; both must be replaced by the recommended natural key.
- **`cash_flow.surrogate_key` is declared WITHOUT `required=True`** (line 186) unlike its siblings — cosmetic

- **Symbol-required inconsistency:** `balance_sheet`, `cash_flow`, `financial_ratios`, `enterprise_values`,

- **All surrogate_key columns recommended `drop`:** every stream here has a clean composite natural key in its own

  single-column key, the fallback is `keep→hash(PK)` (hash only the recommended PK fields) rather than dropping —

### Open decisions
- **Snapshot bulks: N vs P2 (history vs latest-only).** All eight date-less / snapshot-style streams (`company_profile_bulk`, `stock_rating_bulk`, `dcf_valuations_bulk`, `financial_scores_bulk`, `price_target_summary_bulk`, `upgrades_downgrades_consensus_bulk`, `key_metrics_ttm_bulk`, `ratios_ttm_bulk`, `stock_peers_bulk`) are recommended **N** (key on `["symbol"]`, overwrite, keep latest). FMP serves only the current value from these bulk endpoints and offers dated historical endpoints elsewhere for several of them. If the user wants to retain a point-in-time history of any of these from the tap itself, switch that stream to **P2**: add a synthetic `_fmp_extracted_date` (truncate to the chosen grain, e.g. day) and use `["symbol","_fmp_extracted_date"]`. Tradeoff: N gives one clean row per symbol with no growth; P2 preserves history but grows by symbol-count every capture and double-counts if synced more than once per grain. Recommendation: **N for all eight** unless a specific history requirement exists.
- **`stock_rating_bulk` / `dcf_valuations_bulk` carry a `date`.** They look T-eligible, but the bulk endpoint returns only the single current row per symbol (the `date` is the computation date, not an enumerated period). Recommended **N on `["symbol"]`**. Only choose **T** (`["symbol","date"]`) if you confirm FMP actually emits multiple dated rows per symbol from these *bulk* endpoints; the non-bulk historical ratings/DCF endpoints are the proper source for history.
- **`etf_holder_bulk` natural key.** Recommended `["symbol","asset"]` (ETF × held security). If `asset` is ever null/blank for some rows, fall back to `["symbol","cusip"]` or `["symbol","isin"]`. Confirm `asset` uniqueness per ETF before adopting.
- **`reported_currency` in statement PKs.** Included to disambiguate filers that report the same fiscal period in two currencies. If the user is certain FMP only ever returns one currency per (symbol, fiscal_year, period), drop it and use `["symbol","fiscal_year","period"]`. Recommendation: keep it — it is cheap insurance and already in every statement/growth schema.

- **`surrogate_key` column fate = `drop` for every bulk stream.** Each has a clear composite natural key, so the column is redundant. If downstream joins need a single-column key, switch the chosen streams to `keep→hash(PK)` (redefine `generate_surrogate_key` to hash ONLY the recommended PK fields) instead of dropping — but never leave it as the whole-row hash. - **`_part` must be excluded from PK and from any hash.** `PaginatedBulkStream.post_process` sets `row["_part"]` (line 95) *before* `super().post_process` runs `generate_surrogate_key` over `sorted(data.keys())`, so today `_part` pollutes the surrogate hash for `company_profile_bulk` and `etf_holder_bulk`. - **`eod_bulk` leftover `surrogate_key`.** PK override is correct, but the schema still declares `surrogate_key` (`required=True`) and `IncrementalDateStream`→`FmpSurrogateKeyStream` still sets `_add_surrogate_key=True`, so the unused whole-row hash is still computed and stored. Drop the column (or set `_add_surrogate_key=False`) for cleanliness. Also note the synthetic skip-record path (lines 1400-1410) emits `symbol="__TIMEOUT_FAILURE__"` rows that will land as real PK rows under `["symbol","date"]` — harmless but worth filtering downstream.
- **`stock_rating_bulk` `date` and `earnings_surprises_bulk` `date`/`last_updated` are `DateType`** (good for keying). The statement streams' `accepted_date` is a `DateTimeType` (filing metadata, not a key candidate). None of the snapshot bulks (`financial_scores_bulk`, `price_target_summary_bulk`, `upgrades_downgrades_consensus_bulk`, `key_metrics_ttm_bulk`, `ratios_ttm_bulk`, `stock_peers_bulk`, `company_profile_bulk`) carry a native period/date column — confirming P2 (not T) would be the only history option for those.
- **`income_statement_growth_bulk` lacks `reported_currency`?** It DOES declare it (line 847), as do all four growth/statement streams — so the recommended PK with `reported_currency` is formable without a schema change for every statement and growth stream.

### Open decisions
- **stock_grades PK composition** — recommended `["symbol","date","grading_company","new_grade"]`. A single symbol-day can carry several grade actions from different firms, and a firm could issue more than one action on the same date. `grading_company` is the minimum disambiguator; adding `new_grade`/`action` covers same-firm same-day duplicates. Tradeoff: if FMP ever emits two truly-identical (symbol,date,company,grade) rows they would collapse — acceptable since they would be indistinguishable anyway. Confirm whether you'd rather treat this as an append-only event (E) keyed on a synthetic capture instead; T is recommended because the row carries a real `date`.
- **price_target_consensus / price_target_summary / stock_grades_consensus / rating_snapshot history** — recommended N (latest-only, overwrite on `["symbol"]`) since these are date-less recomputed snapshots and FMP exposes no historical variant for them. If you actually want a daily trail of how consensus/scores drifted, switch to **P2**: add `_fmp_extracted_date` (truncated to day) and key `["symbol","_fmp_extracted_date"]`. Tradeoff: P2 grows one row/symbol/day forever vs. N keeps only current state. Recommendation: N, because `historical_ratings` and `historical_stock_grades` already provide the time series for the ratings/grades scores.
- **ipos_disclosure / ipos_prospectus event key** — recommended `["symbol","accepted_date","form"]`. If the `url` column is reliably populated (it is in the schema) prefer the cleaner `["url"]` since one filing = one url. Confirm whether `url` is always present; if it can be null, fall back to the composite. Tradeoff: `url` is the most stable identity but null-prone composite keys risk collisions.

### Notes
- **rating_snapshot has NO primary key AND no surrogate key.** It extends `CompanySymbolPartitionStream` → `BaseSymbolPartitionStream` → `FmpRestStream`, none of which set `primary_keys` (only `FmpSurrogateKeyStream` at client.py:394 does) and it leaves `_add_surrogate_key=False`. So it inherits singer-sdk's empty default PK and emits no dedup key at all — the Postgres loader has nothing to UPSERT on, producing pure append (every sync re-inserts every symbol). This is a real defect independent of the whole-row-hash bug; recommend adding `primary_keys=["symbol"]`. Its schema has no `surrogate_key` property either, so the fix is "add a natural PK," not "redefine surrogate_key."
- **Surrogate-key dup mechanism for the snapshot/series streams.** `analyst_estimates` (via `SymbolPeriodPartitionStream`→`FmpSurrogateKeyStream`), `price_target_summary`, `price_target_consensus`, `stock_grades`, `historical_stock_grades`, `stock_grades_consensus`, and all the news/calendar streams set `primary_keys=["surrogate_key"]` with `_add_surrogate_key=True`. `post_process` (client.py:386) hashes `sorted(record.keys())` over the FULL record (helpers.py:141), so any value change (estimate, price target, score, count, amount) mints a new PK and inserts a duplicate row. Every one of these needs the PK swapped to the natural composite above.
- **`stock_grades` schema field `date` is not `required`** (it's `th.Property("date", th.DateType)` without `required=True`); if `date` can be null, the recommended `["symbol","date",...]` PK has a nullable component. Same for `historical_stock_grades.date`, `dividends_*.date`, `stock_split*.date`, `ipos_calendar.date`. Postgres PK columns must be NOT NULL — recommend marking the chosen key fields `required=True` (or guaranteeing non-null in post_process) when changing the PK. `earnings_calendar.date` and `historical_ratings.date` are already `required=True`.
- **dividends_company/dividends_calendar, earnings_report/earnings_calendar, stock_split_details/stock_splits_calendar are duplicate datasets** (per-symbol endpoint vs. date-windowed calendar endpoint, identical schemas) landing in separate tables. Both get the same `["symbol","date"]` key recommendation; flagging that they will hold overlapping rows by design.
- **ipos_disclosure / ipos_prospectus inherit `replication_key="filing_date"`** but extend `TimeSliceCalendarStream` whose base `replication_key="date"` and `is_timestamp_replication_key=True`; `filing_date` is a `DateType` (not datetime). Not a PK issue, but the timestamp-replication flag on a date field is worth a glance.
- **ipos_calendar has a field named `daa`** (`th.DateTimeType`) — almost certainly a typo for `date`/`day`; not load-bearing for the PK (use `date`) but noting the likely schema typo.

### Open decisions
- **custom_dcf / custom_dcf_levered — N (`["symbol","year"]`, latest-only) vs P2 (`["symbol","year","_fmp_extracted_date"]`, snapshot history).** These rows have a `year` but no observation `date`, and FMP recomputes every model field (price, beta, WACC, equity value per share, ufcf, terminal value, …) against the *current* quote on each request — so the same `(symbol, year)` row's numbers drift every sync. - **market_risk_premium — N (`["country"]`, latest-only) vs P2 (add `_fmp_extracted_date`).** Date-less per-country snapshot. Recommendation: **N**, since FMP exposes only the current premium table and these values move slowly. Tradeoff: you won't retain the historical evolution of each country's premium; if that history is desired, add `_fmp_extracted_date` (P2) at e.g. monthly grain.
- **dcf_valuation / levered_dcf — confirm `["symbol","date"]` is acceptable as-is.** This treats the endpoint as a revisable dated series (one row per valuation date, revisions overwrite). If instead the user wants to snapshot the value computed on *every* sync (not just per distinct `date`), they'd need P2; recommendation is to keep the current `["symbol","date"]` (T) — it is already correct and matches the audit's intent.

- **biggest_stock_gainers / biggest_stock_losers / top_traded_stocks (PIT history vs latest-only):** These are the three flagged date-less live leaderboards.   - **Alternative: N** with PK `["symbol"]` (latest leaderboard membership only, overwrite each sync) if you don't want movers history at all — cheapest, no schema change, but loses the time dimension entirely (and a symbol leaving the leaderboard leaves a stale row unless the loader does full-table replace).
  - **Status-quo fallback only if neither is acceptable:** `keep→whole-row (PIT)` — every distinct observation becomes its own row via the existing hash. This is the current behavior; it "works" only as accidental append-growth keyed on price churn, has no clean dedup key, and is NOT recommended (prefer P2).
- **exchange_market_hours / all_exchange_market_hours (N vs P2):** Recommended **N** (`["exchange"]`, overwrite) because the only volatile field is the `is_market_open` boolean that flips every sync — capturing its history is low value and would otherwise generate two rows per exchange per day under the current whole-row hash. If the user genuinely wants an open/closed timeline, switch to P2 with `_fmp_extracted_date` and PK `["exchange","_fmp_extracted_date"]`; tradeoff is volume of near-duplicate rows.
- **Snapshot streams (T grain confirmation):** `market_sector_performance_snapshot`, `industry_performance_snapshot`, `sector_pe_snapshot`, `industry_pe_snapshot` are keyed on `["date", sector|industry, "exchange"]`. They are flagged restatable T because the current day's snapshot value can change as the trading day finalizes; same-key overwrite is desired. If FMP only ever publishes a finalized end-of-day value, behavior is identical to the historical_* streams — either way T is correct.

### Notes
- **Whole-row hash duplicate bug (all 13 streams):** Every stream here keys on `surrogate_key` = hash of all fields. For the snapshot/historical streams, `average_change`/`pe` revisions, and for the leaderboards the constantly-churning `price`/`change`/`changes_percentage`, mean a re-sync of the same logical row produces a different hash → duplicate insert. This is the core defect for the whole family.
- **`is_market_open` is the duplicate driver for both market-hours streams:** the flag flips open↔close at least twice per trading day, guaranteeing the whole-row hash produces ≥2 rows per exchange per day today. Switching to PK `["exchange"]` (treatment N) fixes it.
- **No real natural-key schema gap for the T/N streams:** all the date-bearing snapshot/historical streams already carry `date` + `sector`/`industry` + `exchange`, and the market-hours/holidays streams already carry `exchange` (+ `date` for holidays), so the recommended PKs can be formed by dropping `surrogate_key` with NO schema additions.
- **Schema addition required ONLY for the three leaderboards** to reach P2 — they need a new `_fmp_extracted_date` (or `_fmp_extracted_at`) column populated in `post_process`; this is the only family member that cannot form a clean PK from existing fields.
- **`changes_percentage` field name:** present in all three leaderboard schemas (FMP source field `changesPercentage`, cleaned by `clean_json_keys`); it is a churning numeric, not a key candidate — listed only to underline why these need a synthetic date for PIT.
- **`HistoricalMarketPerformanceStream` base (l.12-20):** sets `primary_keys=["surrogate_key"]`/`_add_surrogate_key=True` and merges `context` (the per-sector/industry partition) into `query_params`; the partition's sector/industry value is NOT guaranteed to land in the record unless FMP echoes it — verify the payload actually returns `sector`/`industry` so `["date","sector","exchange"]` is fully populated (schema declares the column, but if FMP omits it on the historical endpoints the PK degrades to `["date","exchange"]` and would collide across partitions). Confirm before dropping the surrogate.

- **News `url` vs `symbol`+`url` for symbol-partitioned feeds (`press_releases`, `stock_news`, `crypto_news`, `forex_news`):** I recommend keying on `url` ALONE so the same article surfaced under several symbol partitions collapses to one row. ### Open decisions
- **13F extract/analytics composite key granularity** (`institutional_ownership_extract`, `form_13f_filings_extracts_with_analytics`): I recommend `["cik","date","security_cusip","shares_type","put_call_share"]`. ### Open decisions
- **Holdings / weighting / exposure / info history (etf_and_fund_holdings, etf_and_fund_country_allocation, etf_asset_exposure, etf_sector_weighting, etf_and_mutual_fund_info).** These are date-less current snapshots whose values drift every sync. Recommendation: **N (latest-only overwrite)** on the natural key above — FMP exposes the quarterly `mutual_fund_disclosures` endpoint for true point-in-time portfolio history, so duplicating these live snapshots is redundant. If the user explicitly wants a time series of an ETF's composition between disclosure filings, switch each to **P2** by adding `_fmp_extracted_date` (truncated to the chosen grain) to the PK, e.g. `["symbol","asset","_fmp_extracted_date"]` / `["symbol","sector","_fmp_extracted_date"]` / `["symbol","_fmp_extracted_date"]`. Tradeoff: P2 grows unboundedly and needs a synthetic capture column; N keeps one current row but loses inter-filing snapshots. My recommendation is N for all five.
- **earnings_transcripts surrogate_key (FRAGILE re-release).** A transcript is logically immutable per (symbol, year, quarter), but FMP sometimes re-publishes corrected `content` (and occasionally `date`). With the natural PK `["symbol","year","quarter"]`, a re-release UPDATEs the row (recommended). If the user wants to retain every released version, instead use **P2** `["symbol","year","quarter","_fmp_extracted_date"]` and keep the whole-row hash — but that means re-runs of the same sync day will still collide on content changes. Recommendation: natural PK + `keep→hash(PK)`.
- **mutual_fund_disclosures composite (T vs revisable).** N-PORT filings can be amended (NPORT-P/A), changing `balance`/`val_usd`/`pct_val` for the same security and quarter. Treating it as **T** with PK `["symbol","cik","date","cusip"]` means an amendment overwrites the prior row (recommended — keeps one row per security per quarter). If the user wants to preserve both the original and the amended filing, add `accepted_date` to the PK. Recommendation: T overwrite. See Notes — `cusip` may be null for some holdings, which can collapse rows.
- **mutual_fund_and_etf_disclosure_name_search PK.** This is a name-search directory; rows describe fund registration entities (series/class). `series_id`+`class_id` is the most precise natural key. If those are frequently null in practice, fall back to `["cik","class_id"]` or treat the whole result as N on `["entity_name","series_name","class_name"]`. Recommendation: `["series_id","class_id"]` pending confirmation those are reliably populated.

### Notes
- **No declared natural PK on any stream.** Every stream in this family relies solely on `surrogate_key` (whole-row hash) as its PK; none declares a real natural key. This is the root cause of unbounded duplication on every changing field (holdings weights, nav, no_of_transcripts counter, re-released transcript content).
- **available_transcript_symbols — counter forces whole-row dups.** `no_of_transcripts` increments as new transcripts are released, so the whole-row hash changes each sync and a new row is inserted for the same `symbol` every time the count moves. Keying on `["symbol"]` fixes this; the counter then simply overwrites.
- **mutual_fund_disclosures — `cusip` can be null.** Some N-PORT line items (derivatives, cash) lack a CUSIP; if `cusip` is null the composite `["symbol","cik","date","cusip"]` can collapse multiple holdings into one PK. Consider adding `isin` or `name` as a tiebreaker, or a position line identifier if FMP exposes one. Also: the stream partitions symbol×year(2020→now)×quarter (`partitions` property, lines 219-232), so the year range is hard-coded.
- **mutual_fund_and_etf_disclosure_name_search — `cik` is not unique.** A single CIK (registrant) can file many series/class combinations; `cik` alone cannot be the PK. The schema marks only `symbol` required, but `symbol` may be blank for fund registrations — the recommended `series_id`/`class_id` are the real identifiers and a schema/required-field review is warranted.
- **mutual_fund_and_etf_disclosure — holder identity.** Schema marks `symbol` and `cik` required; `cik` is the holder's identifier in the `-latest` holders view, so `["symbol","cik"]` is sound. `security_cusip` is the fund's own CUSIP (constant per symbol), not a row discriminator.
- **etf_and_fund_country_allocation — `weight_percentage` typed as String** (and cast to str in post_process, lines 123-126), unlike the NumberType weight on the other ETF streams; harmless for keying but inconsistent across the family.
- **latest_earning_transcripts uses `fiscal_year`/`period`** while earnings_transcripts uses `year`/`quarter` and transcripts_dates_by_symbol uses `fiscal_year`/`quarter` — the same logical call is named three different ways across these streams, so any cross-stream join must reconcile (fiscal_year≈year, period≈quarter).
- **earnings_transcripts `state_partitioning_keys = ["symbol"]`** (lines 44) deliberately drops year/quarter from the bookmark to stay under `elt.buffer_size`; this is a state/throughput choice and does not affect the PK recommendation.

### Open decisions
- **index_short_quote & all_index_quotes (P2 vs N):** these use `SHORT_QUOTE_SCHEMA` with NO time field, yet are live snapshots. Recommend **P2** — add a synthetic `_fmp_extracted_date` (truncated to the chosen capture grain, e.g. day) and PK `["symbol","_fmp_extracted_date"]` if intraday/periodic price history of indexes is wanted; otherwise **N** with PK `["symbol"]` for latest-only. Tradeoff: P2 grows one row per symbol per capture window (and the grain must match sync cadence to avoid either collapsing distinct observations or unbounded growth); N keeps exactly one row per index but discards history. Note `index_quote` already provides PIT history for indexes via its native `timestamp`, so N is the lighter-weight choice for the short variants unless a dedicated low-payload PIT feed is desired.
- **index_quote (drop vs keep surrogate):** recommend `drop` and PK `["symbol","timestamp"]`. If a single-column join key is needed downstream, switch to `keep→hash(PK)` over `["symbol","timestamp"]`. Tradeoff is only the extra column.
- **historical_*_constituent date granularity:** PK `["symbol","date"]` assumes FMP never emits two events for the same symbol on the same calendar date (e.g. removed and re-added same day). This is essentially never true for index membership changes, so `["symbol","date"]` is safe; if a paranoid guard is wanted, add `date_added` or `reason` to the key. Recommend keeping `["symbol","date"]`.

### Notes
- **Confirmed-correct streams (no change needed):** ALL chart streams (company_chart_light/full, company_unadjusted_price, company_dividend_adjusted_prices), ALL interval price streams (company_prices_1min/5min/15min/30min/1h/4h, index_1min/5min/1h, historical_index_light_chart, historical_index_full_chart), and ALL nine technical-indicator streams. They have no `surrogate_key` schema property and never populate one — the buggy whole-row hash does not apply.
- **Buggy streams sharing the surrogate-key defect:** index_list, index_quote, index_short_quote, all_index_quotes, sp500_constituent, nasdaq_constituent, dow_jones_constituent, historical_sp500_constituent, historical_nasdaq_constituent, historical_dow_jones_constituent. All extend `FmpSurrogateKeyStream` (or set `primary_keys=["surrogate_key"]` + `_add_surrogate_key=True` directly), so the whole-row hash is the PK and any field drift (price, market_cap, sector, name) inserts a duplicate logical row on each sync.

Confirm whether both streams are needed.
- **DateType vs DateTimeType inconsistency (not a PK bug, but a join hazard):** the technical-indicator base schema and interval price schema declare `date` as `DateTimeType` (carries time-of-day for intraday bars), while ChartLight/ChartFull/Adjusted price schemas declare `date` as `DateType`. The `["symbol","date"]` PK is correct in both cases, but downstream joins across these tables must account for the type difference.
- **historical_*_constituent schema field name overlap:** the schema has both `date` (DateType, the change date — used in the recommended PK) and `date_added` (StringType, a descriptive added-date). The PK uses `date`; `date_added` is descriptive only. No schema change needed to form the recommended PK.
- **Constituent natural key requires `symbol`:** all six constituent/historical-constituent streams expose `symbol` in their schema, so the recommended natural/composite keys can be formed without any schema change.
